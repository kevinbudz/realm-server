# Runtime timing and behavior-scheduler comparison

Compared target [`bb75bc1e438b465986a8ada354b6332f69e0e3a6`](https://github.com/kevinbudz/realm-server/tree/bb75bc1e438b465986a8ada354b6332f69e0e3a6) with candidate reference [`6fd20aad4a7905b13f25389c68368a942a2b68cb`](https://github.com/ossimc82/fabiano-swagger-of-doom/tree/6fd20aad4a7905b13f25389c68368a942a2b68cb) (2015-11-09). This is a static source comparison; no runtime replay was performed.

## Main conclusion

The core movement and attack timers use the same real-time units in ordinary conditions, so the inspected timing loop does not show a general multiplier that would make enemies move or fire faster. There is, however, a high-confidence target scheduler mismatch: target `Prioritize` interprets child `bool` results as “still running,” while reference `Prioritize` consumes explicit `CycleStatus`. Since target `Wander` returns true indefinitely whenever un-paralyzed, it can become the permanent selected fallback and prevent `Follow` and `StayAbove` from being reconsidered. This can make an enemy continue wandering after it should resume following; it is an engagement/arbitration issue, not increased movement velocity.

## Tick interval, movement units, and cadence

Target calls `Settings.Init()` at startup (`Program.cs:104, 113`), reads `TicksPerSecond` from `Settings.xml`, and derives both `MillisecondsPerTick` and `SecondsPerTick` (`Common/Settings.cs:63-65`; its fallback when no file exists is 5 TPS). The checked-in target config sets 10 ticks/sec, or 100 ms/tick (`Settings.xml:8-9`). `Manager.Tick` advances a world when its tick deadline is reached and accounts time in fixed `MillisecondsPerTick` steps (`Game/Manager.cs:1077-1080, 1202-1205`). The reference derives `MsPT = 1000/TPS` and sets `thisTickTimes = times * MsPT` on each logic step (`wServer/realm/LogicTicker.cs:25-34, 61-76`); its launcher supplies 20 as the default TPS (`wServer/Program.cs:47-50`). Either deployment can override its checked-in/default setting.

At normal load, movement behaviors convert their speed parameters to units/second and multiply by elapsed seconds per tick. Target `Follow` and `Wander` use `Settings.SecondsPerTick` (`Game/Logic/Behaviors/Follow.cs:80-88`, `Wander.cs:36-46`); reference equivalents use `time.thisTickTimes/1000f` (`wServer/logic/behaviors/Follow.cs:74-83`, `Wander.cs:33-54`). Both speed helpers return `5.55 * configuredSpeed + 0.74` when not Slowed (`Utils/MathUtils.cs:103-109`; `wServer/realm/Utils.cs:188-193`). For example, `Follow(1)` moves at 6.29 world units/sec in either implementation when not slowed. The target’s configured 10 TPS therefore uses a 0.629-unit step per tick versus 0.3145 at a reference 20 TPS, but these are the same nominal distance per second; target updates are coarser, not faster in aggregate. The slowed formula differs and is documented separately by the primitive comparison.

Target `Shoot` stores cooldowns in milliseconds, subtracts exactly one configured tick interval before testing whether the cooldown is due, then reloads the configured cooldown after a shot (`Game/Logic/Behaviors/Shoot.cs:54-55, 57-68, 142-147`). Reference `Shoot` tests `cool <= 0` before subtracting that tick's elapsed milliseconds (`wServer/logic/behaviors/Shoot.cs:65-75, 117-126`). After a shot resets the timer to positive cooldown `C`, target's next repeat interval is `ceil(C/dt) * dt`; reference's interval is `(ceil(C/dt) + 1) * dt` because the check happens before the decrement. With checked target 10 TPS and reference default 20 TPS, a 500 ms shot cooldown repeats every 500 ms in target and every 550 ms in reference; a 51 ms cooldown repeats every 100 ms in target and every 150 ms in reference; a 525 ms cooldown repeats every 600 ms in both; and a 750 ms cooldown repeats every 800 ms in both. Under these two tick settings and fixed positive cooldowns, target is equal or up to one 50 ms reference tick faster, not globally faster by a large factor. The initial offset-zero shot happens on the first behavior tick after entry in both (target `Shoot.Enter`, `:57-61`; reference `Shoot.OnStateEntry`, `:45-48`, called when entity state entry is processed at `wServer/realm/Entity.cs:152-167`). The companion helper-level comparison covers cooldown variance and predictive-shot differences.

Under load, the time-step strategy differs: reference `LogicTicker` can fold multiple missed intervals into one `thisTickTimes` (`LogicTicker.cs:61-76`), whereas target advances through fixed-size world ticks using its fixed step (`Manager.cs:1077-1080, 1202-1205`). This affects update granularity and catch-up behavior under lag; it does not establish a faster normal movement or attack rate.

## High-confidence scheduler mismatch: `Prioritize` can stick on target `Wander`

Target behavior classes use `bool Tick(Entity)`. Target `Prioritize.Tick` keeps ticking its current child while that child returns true and only chooses from the beginning of its priority list when the child returns false (`Game/Logic/Behaviors/Prioritize.cs:23-43`). Target `Wander.Tick` returns false only while paralyzed; during every ordinary tick it moves and returns true (`Game/Logic/Behaviors/Wander.cs:29-46`). As a result, once `Wander` is selected, `Prioritize` does not revisit higher-priority children until that composite exits.

The reference contract is different. Reference `Prioritize` takes `CycleBehavior` children and selects/retains the child by `CycleStatus`: it starts at index -1, scans for `InProgress`, then resets its selected child to -1 when that child is `Completed` or `NotStarted` (`wServer/logic/behaviors/Prioritize.cs:13-54`). Reference `Wander` marks itself `Completed` on the tick where it chooses a new direction and `InProgress` while traveling that segment (`wServer/logic/behaviors/Wander.cs:29-40`). That cycle releases the fallback periodically so the priority stack is scanned again.

The behavior stack is shared by real enemy definitions: target Hobbit Archer has `Prioritize(StayAbove(0.4, 9), Follow(0.75, range: 6), Wander(0.4))` at `Game/Logic/Database/Lowland.cs:32-36`; the reference definition has the same stack at `wServer/logic/db/BehaviorDb.Lowland.cs:32-36`. White Demon provides another direct match at target `Game/Logic/Database/Mountain.cs:49-56` and reference `wServer/logic/db/BehaviorDb.Mountain.cs:14-21`.

Static execution example (not runtime-tested): if `StayAbove` is inactive and `Follow` has reached its rest range, target `Prioritize` tries `Wander`; it moves and returns true, so subsequent ticks call only that `Wander`. If the player then moves beyond follow range, `Follow` is never checked and the enemy keeps wandering until the composite is exited. In the reference, the wandering segment eventually marks `Completed`, clears the selection, and the next scan can choose `Follow` again if the player is in acquisition range. This is a plausible cause for enemies that wander instead of resuming pursuit, but it does not prove a faster walk/run speed.

Confidence: high for the control-flow difference (directly follows from the implementations); medium for its prevalence in play because it depends on the terrain and encounter entering the stated conditions. No execution test was run.

## State ticking and transition ordering

Target initializes a chain of active states from the root toward the deepest first child (`Game/Entity.cs:587-617`). Each eligible world tick then runs root behaviors, runs each active state’s behaviors outer-to-inner, and only afterward checks active-state transitions outer-to-inner; the first transition in a level wins (`Game/Entity.cs:620-659`). A transition switches state after those behavior calls and target behaviors for the newly entered state begin on the next entity tick (`Game/Entity.cs:661-705`).

Reference retains the current deepest state and walks that state toward its parents. It checks transitions at each level before ticking that level’s behaviors; after any transition succeeds it prevents additional transitions but still finishes ticking behaviors along the old state path for that tick (`wServer/realm/Entity.cs:152-193`). `Transition.Tick` switches `CurrentState` immediately and marks a state-entry event that is handled on a later tick (`wServer/logic/Transition.cs:32-46`; `Entity.cs:125-134, 152-193`).

This is a concrete arbitration-order difference when multiple active ancestor/descendant transitions become true on the same tick: target chooses the outermost transition first; reference chooses the deepest transition first. It can change which phase an enemy enters, but no shared enemy definition was validated here where competing transitions are simultaneously true, so this remains a potential phase-selection difference rather than a demonstrated source of faster behavior. The overworld and boss definition audits are the right places to tie it to a specific phase.

## Two transition and target-selection integration defects

**Target root transitions are discarded; the shared Scarab example never reaches its chase state.** A target `BehaviorModel` keeps top-level entries only when they are `Behavior`, `Loot`, or `State` (`Game/Logic/BehaviorDb.cs:24-39`). `Transition` implements `IBehavior` directly rather than deriving from `Behavior` (`Game/Logic/Transition.cs:8`), and transitions are collected into a state's transition list only by `State` (`Game/Logic/State.cs:18-40`). The target Scarab passes `NoPlayerWithinTransition` and `PlayerWithinTransition` as root-level `db.Init` arguments before declaring its `Idle` and `Chase` states (`Game/Logic/Database/Tomb.cs:554-564`), so those transitions are not stored or ticked. `Entity.InitStates` selects the first root state and then its first child (`Game/Entity.cs:587-617`); for this definition that is `Idle`/`Wander`, and no active transition enters `Chase`/`Follow`/`Shoot`. The reference has the same two transitions inside a root `State`, where `State` collects transitions, and nests `Idle` and `Chase` beneath it (`wServer/logic/db/BehaviorDb.Tomb.cs:279-290`). This is a high-confidence target-only registration/control-flow defect with a concrete consequence: the target Scarab cannot switch into its chase-and-shoot phase through the declared player-distance conditions.

**Target generic nearest-entity lookup includes the host itself.** Target regular enemies are inserted into `EntityChunks` (`Game/World.cs:636-640`), and `ChunkController.HitTest` returns every entity in range without excluding the queried entity (`Game/ChunkController.cs:98-115`). `GetNearestEntity` chooses the closest result without a self filter (`Utils/GameUtils.cs:30-48`); `GetNearestPlayer` instead scans player chunks and filters Invisible (`Utils/GameUtils.cs:199-219`). Reference helper `GetNearestEntity(dist, objType:null)` explicitly means player lookup and scans `PlayersCollision`, filtering pets and invisible players (`wServer/realm/Utils.cs:50-52, 75-96`); reference `Orbit` with a null target uses that helper (`wServer/logic/behaviors/Orbit.cs:57-58`).

A concrete target effect is Limon the Sprite God's `circle_player` `Prioritize`: after `StayCloseToSpawn` is satisfied, it has `Orbit(speed:1.8, radius:4, acquireRange:5, target:null)` before two Follow fallbacks (`Game/Logic/Database/SpriteWorld.cs:99-106`). If there is no visible player within 5 units but at least one player remains within the enemy tick's sight radius, the target Orbit fallback resolves to its own host. Its coincident-position branch chooses a random angle, then moves toward a point on a radius-4 circle around that self position and reports active (`Game/Logic/Behaviors/Orbit.cs:59-83`). The reference null-target helper cannot select the host (`wServer/logic/behaviors/Orbit.cs:57-58`; helper implementation at `wServer/realm/Utils.cs:50-52, 75-96`). The reference Limon state machine uses a different movement stack and does not provide a directly matched null-target Orbit comparison (`wServer/logic/db/BehaviorDb.SpriteWorld.cs:10-49`); this example demonstrates target self-selection semantics, not a claim that the reference has identical phase definitions. This yields target-only circling/jittering in the acquisition gap and prevents the lower-priority Follow children from being considered while Orbit returns true. It is condition-dependent; target skips ordinary behavior ticks when there is no player anywhere within sight radius and no condition effects (`Game/Entity.cs:628-633`).

The same self fallback affects target `StayBack`: with no player and no named target, the host is selected, the zero vector is normalized, an unchanged position is passed to `ValidateAndMove`, and the behavior returns true (`Game/Logic/Behaviors/StayBack.cs:24-35`). Reference StayBack queries a player and remains `NotStarted` when no player exists (`wServer/logic/behaviors/StayBack.cs:30-54`). Where a target `StayBack` is in a `Prioritize` stack, self-selection can therefore lock the stack on a no-op child rather than release it for later fallbacks. This is a helper/composite integration consequence; do not characterize it as increased movement speed.

Target `NoPlayerWithinTransition` also checks both `GetNearestPlayer` and generic `GetNearestEntity` (`Game/Logic/Transitions/NoPlayerWithinTransition.cs:14-17`), so the generic part can see self for regular enemies. A concrete nested call exists in target Steel Bot's `Attack` state at radius 30 (`Game/Logic/Database/Mountain.cs:300-308`), with a corresponding reference transition in its Attack state (`wServer/logic/db/BehaviorDb.Mountain.cs:334-340`). The false self-hit is real when that transition is evaluated, but target `TickStates` skips un-effected enemies when no player is within the sight radius (`Entity.cs:628-633`); consequently this example alone does not establish that Steel Bot stays in Attack indefinitely after all players leave. The root-transition Scarab finding above is the stronger complete state-change failure.

## Sequence cadence caveat without a matched target callsite

Target `Shoot.Tick` returns false while a due shot is stunned (`Game/Logic/Behaviors/Shoot.cs:64-70`) and while its cooldown is not due (the cooldown path later returns false); target `Sequence` advances on any child returning false (`Game/Logic/Behaviors/Sequence.cs:23-35`). Reference Shoot instead reports `InProgress` while waiting and reference Sequence advances only on `Completed` or `NotStarted` (`wServer/logic/behaviors/Sequence.cs:35-45`). This could change composed attack spacing, but the target database has no `new Sequence(...)` callsite. Reference has a Sequence in Leviathan (`wServer/logic/db/BehaviorDb.Mountain.cs:491-508`), while target Leviathan uses state/timed-transition phases instead (`Game/Logic/Database/Mountain.cs:401-430`). Therefore this is not a matched active-enemy explanation for the reported firing cadence and is excluded from the main findings.

## Scope and limits

This is static source comparison, not a live timing benchmark. Runtime behavior depends on the deployed `Settings.xml`, reference TPS override, actual lag, map elevation, active-player radius, and condition effects. Primitive-specific differences (cooldown variance rounding, slowed speeds, movement details, and projectile prediction) are being handled by the helper comparison. On the evidence reviewed here, the strongest actionable timing explanation is the target `Prioritize`/`Wander` status mismatch; the core per-second movement and cooldown units are otherwise aligned.
