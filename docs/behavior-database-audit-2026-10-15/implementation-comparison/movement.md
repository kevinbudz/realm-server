# Movement behavior implementation comparison

Compared target [`bb75bc1e438b465986a8ada354b6332f69e0e3a6`](https://github.com/kevinbudz/realm-server/tree/bb75bc1e438b465986a8ada354b6332f69e0e3a6) with reference [`6fd20aad4a7905b13f25389c68368a942a2b68cb`](https://github.com/ossimc82/fabiano-swagger-of-doom/tree/6fd20aad4a7905b13f25389c68368a942a2b68cb) (2015-11-09). This is a source comparison, not a runtime replay. Findings concern movement, target acquisition, and movement scheduling; projectile cadence is covered separately.

## Answer: can the implementation change speed with equivalent definitions?

For ordinary, un-slown movement where both definitions pass the same `speed` parameter and both servers tick on schedule, the core conversion is the same. Target `GetSpeed` is `5.55 * speed + 0.74` (`Utils/MathUtils.cs:103-110`); reference uses the same formula (`wServer/realm/Utils.cs:188-193`). Both then advance by that value times elapsed seconds: target uses `Settings.SecondsPerTick` in `Follow.cs:86-87` and `Wander.cs:43-45`; ref uses `time.thisTickTimes / 1000f` in `Follow.cs:81-83` and `Wander.cs:50-54`. So equal settings do not show a systematic base-speed multiplier difference in Follow or Wander.

Tick delivery/configuration still matters. The checked-in target `Settings.xml` sets 10 ticks/s (`Settings.xml:8-9`), or 100ms per tick; `Common/Settings.cs:63-65` has a 5TPS fallback (200ms) only if config omits the value. Target movement uses the configured fixed `1/TicksPerSecond`; the reference behavior receives the actual measured `thisTickTimes`. If the reference runtime delivers irregular ticks, or a deployment changes target TPS, motion timing can diverge even though the movement formula is normalized by elapsed time.

There is one verified conditional speed difference in the shared helper: under `Slowed`, target returns `(5.55 * speed + 0.74) / 2`, while reference returns `2.22 * speed + 0.74` (same source citations above). The shared Elf Swordsman definition includes `Wander(0.4)` in both DBs (`Game/Logic/Database/Lowland.cs:247-255`; `wServer/logic/db/BehaviorDb.Lowland.cs:265-276`). For that setting, normal speed is 2.96 units/s in both; while slowed it is 1.48 target vs 1.628 ref, so target is about 9.1% slower. At `Follow(1)`, the same formulas give 3.145 target vs 2.96 reference while Slowed, making target about 6.25% faster in that conditional example. The formulas meet at speed `2/3`; direction depends on configured speed. This affects any non-immune enemy that actually receives Slowed; it does not establish that all enemies can be slowed. High confidence in arithmetic/code; player consequence depends on that enemy’s immunity/effect state.

Even when speed magnitude agrees, the implementation can materially change *when and where* movement occurs. The highest-confidence examples are Wander’s direction/priority behavior, Orbit’s handedness/radius and no-player fallback, plus StayBack’s no-player fallback below. Charge has a narrower axis-alignment edge; Follow shows no meaningful pursuit difference after resolving helper semantics. These can look to a player like different pursuit speed or willingness to engage, but are not a general per-second speed scaling change.

## Concrete semantic differences

### Wander chooses a different direction set and has different arbitration cadence

Target `MathUtils.PlusMinus()` returns only `-1` or `+1` (`Utils/MathUtils.cs:97-101`), and target Wander builds `(PlusMinus(), PlusMinus())`, normalizes, then walks that direction for a fixed 0.6 distance-seconds (`Game/Logic/Behaviors/Wander.cs:36-45`). It therefore wanders only along the four diagonals, with a 600ms leg at steady speed. Reference draws each coordinate from `[-1, 0, 1]`, rejects only `(0,0)`, and chooses a 300–700ms leg (`wServer/logic/behaviors/Wander.cs:15-20, 34-55`), allowing cardinal and diagonal directions. The average leg duration is 500ms, but its direction changes are randomized.

Player-visible consequence: wandering routes have no axis-aligned legs on target, and turns occur at a fixed cadence instead of a 300–700ms cadence. Equal `Wander(0.4)` entries for Elf Archer show this is not a DB parameter change (`Game/Logic/Database/Lowland.cs:238-245`; `wServer/logic/db/BehaviorDb.Lowland.cs:254-264`). Confidence: high. This is an implementation difference; which pattern is historically intended is not established by this source comparison.

There is also a priority interaction: target Wander returns `true` every non-paralyzed tick (`Game/Logic/Behaviors/Wander.cs:29-46`), including when it picks a new direction; legacy Wander sets its cycle status to `Completed` on that direction-reset tick (`wServer/logic/behaviors/Wander.cs:29-40, 50-56`). Target Prioritize retains a child while it returns true (`Game/Logic/Behaviors/Prioritize.cs:23-43`); reference releases a child that reports Completed/NotStarted and selects again on the next tick (`wServer/logic/behaviors/Prioritize.cs:27-54`). Thus if fallback Wander is selected while higher-priority Follow is inactive, target can keep wandering after Follow would become applicable; ref rechecks the priority stack at a leg boundary and can switch to Follow. A shared Hobbit Archer stack orders `StayAbove`, `Follow`, then `Wander` (`Game/Logic/Database/Lowland.cs:32-35`; `wServer/logic/db/BehaviorDb.Lowland.cs:32-36`). Consequence: if Wander becomes active while Follow is inactive, later applicable Follow behavior may be suppressed; this changes pursuit cadence, not Wander’s step speed. Confidence: high in control flow, medium on exact encounter timing. This depends on `Prioritize` consuming the child completion signal.

### Orbit reverses the default orbit direction and target honors radius variance

Reference Orbit always increments the angle by positive `GetSpeed(speed)/radius` (`wServer/logic/behaviors/Orbit.cs:57-75`), which traces clockwise in the game’s screen coordinates (positive Y is down). Target adds `orbitClockwise=false` by default and maps false to direction `-1` (`Game/Logic/Behaviors/Orbit.cs:24-34, 36-49, 71-82`), so an otherwise equivalent default Orbit runs counterclockwise. Example: shared Elf Mage uses `Orbit(0.5, 3)` with no direction argument in either DB (`Game/Logic/Database/Lowland.cs:257-264`; `wServer/logic/db/BehaviorDb.Lowland.cs:277-284`). Consequence: orbiting enemies circle the opposite way. Confidence: high in the code and coordinate interpretation; no evidence here that the reversal was intentional.

Target also uses sampled `state.Radius` for the orbit goal (`Game/Logic/Behaviors/Orbit.cs:44-48, 76-82`); reference samples `s.Radius` but uses the original constructor `radius` for the actual goal (`wServer/logic/behaviors/Orbit.cs:32-39, 69-75`). Thus reference’s `radiusVariance` changes angular-speed calculation but not the path radius, while target’s variance changes both. Elf Archer supplies `radiusVariance: 0.5` with radius 3 in both definitions (`Game/Logic/Database/Lowland.cs:238-245`; `wServer/logic/db/BehaviorDb.Lowland.cs:254-264`): target path radius varies about 2.5–3.5 at state entry; reference path remains 3. Consequence: target orbit distance visibly varies. Confidence: high. This may be a target correction to an apparent unused-variance bug in reference; source alone cannot establish intended 2014 behavior.

A shared oddity left in both implementations: omitted `radiusVariance` defaults to `speed * 0.1`, not `radius * 0.1` (target constructor `Orbit.cs:24-33`, ref `Orbit.cs:21-29`). It is not a target/reference difference.

### Generic target lookup includes the target enemy itself

The target `GetNearestEntity(radius)` scans `EntityChunks` without filtering out the host (`Utils/GameUtils.cs:30-48`); entities are inserted into that chunk index at `Game/World.cs:637-640`, and the chunk hit test returns all entities in range without a self exclusion (`Game/ChunkController.cs:98-115`). In the reference, `GetNearestEntity(dist, objType:null)` means visible players only (excluding pets), not arbitrary entities (`wServer/realm/Utils.cs:75-87`). This distinction matters for several target fallbacks:

- **Follow:** target's no-player fallback resolves to itself. Its zero-length vector is within `Range`, so it enters `Resting` and returns `false` rather than chasing itself (`Game/Logic/Behaviors/Follow.cs:48,80-94,114`). Reference simply has no player target. I found no evidence that target Follow chases nearby enemies; withdraw that earlier claim. With visible players, both implementations choose a nearest player and use the same movement step. Confidence: high in no-player behavior; no material general Follow speed difference established.
- **Charge:** the self fallback is rejected by target's unequal-coordinate guard, so it does not charge itself (`Game/Logic/Behaviors/Charge.cs:51-58`). The concrete difference is narrower: target uses `x != || y !=`, while ref requires `x != && y !=` (`wServer/logic/behaviors/Charge.cs:39-45`), so target charges players exactly aligned on one axis where reference does not. Shared Black Bat uses `Charge()` ahead of Wander in Prioritize (`Game/Logic/Database/Midland.cs:303-309`; `wServer/logic/db/BehaviorDb.Midland.cs:335-343`), with the same default speed/range. Consequence is limited to axis-aligned charge triggers, not a continuous speed increase. Confidence: high in code; medium in encounter frequency.
- **StayBack:** target's no-player fallback resolves to itself; `Position.Normalize()` leaves a zero vector unchanged (`Common/Structures.cs:296-307`), then StayBack calls `ValidateAndMove` with the unchanged position and returns `true` (`Game/Logic/Behaviors/StayBack.cs:24-35`). Reference's null-type lookup finds no player and leaves StayBack `NotStarted` (`wServer/logic/behaviors/StayBack.cs:29-54`; helper cited above). In a Prioritize stack, target can therefore hold StayBack and suppress lower-priority Wander while no player is nearby; the shared Elf Wizard's `move3` stack is StayBack then Wander (`Game/Logic/Database/Lowland.cs:220-226`; `wServer/logic/db/BehaviorDb.Lowland.cs:235-241`). Consequence: target Elf Wizard can idle instead of wandering in that phase. Confidence: high assuming normal enemy insertion into EntityChunks (verified above).
- **Orbit:** with no named target, target's fallback resolves to itself while ref's null target query returns no player. Target then sees equal host/target coordinates, draws a fresh random angle, creates a radius-offset goal around the host's current position, normalizes that vector, and advances by `GetSpeed(speed) * dt` (`Game/Logic/Behaviors/Orbit.cs:59-82`). Reference returns without movement when no player is found (`wServer/logic/behaviors/Orbit.cs:53-58`). `ValidateAndMove` applies the requested candidate (collision handling may alter it, but it does not cap it to a lower speed; `Game/Entity.cs:327-339,342-388`). For shared Elf Mage `Orbit(0.5,3)` (`Game/Logic/Database/Lowland.cs:257-264`; `wServer/logic/db/BehaviorDb.Lowland.cs:277-286`), this means target moves at its ordinary nominal `GetSpeed(0.5)=3.515` units/s (about 0.3515 units per configured 100ms tick on an open tile) even without a player, in a fresh jitter direction each tick; ref stays still. This is movement when idle, not an elevated engaged speed. Confidence: high for open passable ground.

Charge’s normal travel step is speed times elapsed seconds in both (`Game/Logic/Behaviors/Charge.cs:68-77`; `wServer/logic/behaviors/Charge.cs:58-67`). The reference sets duration to the smaller of cooldown and estimated travel duration, but compares seconds (`d/GetSpeed`) with cooldown milliseconds before converting (`:43-47`); target uses just estimated travel duration, then starts its cooldown after the charge ends (`:47-77`). For ordinary default values and the default 10-unit range this comparison usually chooses full travel, but custom slow speeds / long ranges can truncate a reference charge. Confidence: high in unit mismatch; practical effect depends on the behavior inputs and whether the distance/speed estimate exceeds the cooldown’s numeric millisecond value.

## Extent and limitations

Reviewed every target class named in the movement request and its same-named compiled reference behavior, plus target-only `MoveLine` and candidate reference `MoveTo`. Confirmed the inspected reference behavior source files are explicit compile items in `wServer/wServer.csproj` (relevant entries: Buzz `:131`, Charge `:135`, MoveTo `:174`, ReturnToSpawn `:184`, Swirl `:189-190`, Orbit `:195`, StayAbove `:198`, StayBack `:200`, Protect `:205`, Follow/Prioritize `:206-207`, and Wander `:214`), and the cited Lowland/Mountain database modules are compiled at `wServer/wServer.csproj:232-236`; no uncompiled/legacy “CubeGod” source was used. Cross-checked shared database examples for `Elf Archer`, `Elf Swordsman`, `Elf Mage`, `Hobbit Archer`, `Elf Wizard`, `Black Bat`, and `Rock Bot` as identified above. The behavioral source comparison is broad across all requested classes, but the concrete DB spot checks are examples, not an exhaustive pairing of every enemy state or every call site. I did not inspect projectile firing implementations here; that is a separate audit. I did not run either server or tests.
