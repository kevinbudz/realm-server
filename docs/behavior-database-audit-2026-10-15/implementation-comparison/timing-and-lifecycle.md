# AI timing and lifecycle helper comparison

Compared target [`bb75bc1e438b465986a8ada354b6332f69e0e3a6`](https://github.com/kevinbudz/realm-server/tree/bb75bc1e438b465986a8ada354b6332f69e0e3a6) with reference [`6fd20aad4a7905b13f25389c68368a942a2b68cb`](https://github.com/ossimc82/fabiano-swagger-of-doom/tree/6fd20aad4a7905b13f25389c68368a942a2b68cb) (2015-11-09). This note covers helpers that can change AI cadence or shot selection beneath database definitions. It is not a full behavior-engine review; broader runner and entity/world tick integration are treated separately. Historical correctness against RotMG 7.0.0 remains unverified.

## Material implementation differences

### `Shoot.predictive` has a different contract

The target interprets `predictive` as a probability: on each shot it compares the value with a fresh uniform random float, and on success projects the target position four history ticks forward (`Game/Logic/Behaviors/Shoot.cs:95-103`; `PredictNumTicks` at `:14`). The reference always applies the value as a multiplier to an estimated angular velocity correction, computed from a target position 100 ms in the past and projectile speed (`wServer/logic/behaviors/Shoot.cs:50-62,83-84`). Thus the same numeric setting does not mean the same lead.

A clean matched example is the Beholder: both definitions use a five-shot, 72-degree fan, projectile index 0, `predictive: 0.5`, and 750 ms cooldown (`Game/Logic/Database/Mountain.cs:155`; `wServer/logic/db/BehaviorDb.Mountain.cs:188`). Target therefore leads on roughly half its volleys using fixed four-tick linear extrapolation; reference applies half of its speed-scaled angular correction on every volley. Treat this as a porting semantic hazard, not proof that either tuning is wrong.

### Target halves shot count while Dazed

Target `Shoot.Tick` changes projectile count to `ceil(Count / 2)` while the host has Dazed (`Game/Logic/Behaviors/Shoot.cs:72-75`). Reference `Shoot.TickCore` fires its configured `count` without a Dazed count adjustment (`wServer/logic/behaviors/Shoot.cs:71-115`). For example, the matched Brown Den Spider has three projectiles at 20-degree spacing and a 500 ms cooldown in both databases (`Game/Logic/Database/SpiderDen.cs:139-145`; `wServer/logic/db/BehaviorDb.SpiderDen.cs:157-165`): under Dazed, target emits two instead of three. This is a target-side combat rule addition; intent is unknown.

### Cooldown variance is tick-quantized only in target

Reference `Cooldown.Next` samples each integer millisecond in the inclusive interval `[-Variance, +Variance]` and adds it to the base cooldown (`wServer/logic/Cooldown.cs:34-38`). Target samples a float-based integer and snaps the result to `Settings.MillisecondsPerTick` using remainder truncation (`Utils/MathUtils.cs:56-60`; used by `Game/Logic/Behaviors/Shoot.cs:142-145`). The target repository configures 10 ticks per second, or 100 ms per tick (`Settings.xml:8`; `Common/Settings.cs:63-65`).

The shared Snakepit Guard shot config is `1000 ± 200 ms` in both DBs (`Game/Logic/Database/SnakePit.cs:376-379`; `wServer/logic/db/BehaviorDb.SnakePit.cs:403-407`). Reference can use every millisecond in 800–1200 ms. Target instead draws a float-based integer and snaps it to 100 ms increments; the half-open input range and truncation/remainder rule make this a coarse bucketed distribution rather than the reference uniform millisecond distribution. The bucket weights are not symmetric, although float rounding near the upper endpoint makes exact endpoint outcomes unsuitable for a simple set claim. This changes the cooldown distribution even though the constructor arguments match. Quantizing to ticks may be deliberate; the resulting distribution is worth validating before changing behavior.

Zero-cooldown normalization itself matches for `Shoot`: target substitutes 1000 ms (`MathUtils.NormalizeCooldown(cooldown, 1000)`, `Game/Logic/Behaviors/Shoot.cs:54`); reference `Cooldown.Normalize()` also substitutes 1000 (`wServer/logic/Cooldown.cs:20-25`). Both initialize the first shot from the configured cooldown offset (target `Shoot.Enter`, `Game/Logic/Behaviors/Shoot.cs:57-62`; reference `Shoot.OnStateEntry`, `wServer/logic/behaviors/Shoot.cs:45-48`). The runner's exact first-tick scheduling is outside this note.

The repeated-shot cadence also differs by one engine tick for cooldowns that land exactly on a tick boundary. Target decrements first, then checks for expiration (`Game/Logic/Behaviors/Shoot.cs:64-68`); reference checks `cool <= 0` first and only otherwise decrements (`wServer/logic/behaviors/Shoot.cs:71-73,117-123`). With checked target config at 10 TPS (100 ms, `Settings.xml:8`; `Common/Settings.cs:63-65`) and reference startup fallback 20 TPS (50 ms, `wServer/Program.cs:47-49`; an external `tps` setting can override it), the shared Brown Den Spider 500 ms shot (`Game/Logic/Database/SpiderDen.cs:143`; `wServer/logic/db/BehaviorDb.SpiderDen.cs:162`) repeats every 500 ms target-side but every 550 ms reference-side. A 750 ms cooldown reaches 800 ms on both at these tick rates; 1000 ms reaches 1000 ms target-side and 1050 ms reference-side. These values follow from the cooldown check order and configured steps; deployments with another reference TPS will change the interval.

### Reproduction position differs with identical Stheno configuration

Target `Reproduce` creates the child at the parent's exact position unless a target-only region option is used (`Game/Logic/Behaviors/Reproduce.cs:61-80`). Reference chooses a random angle and places the child up to `spawnRadius / 2` from the parent; when unset, `spawnRadius` defaults to `densityRadius` (`wServer/logic/behaviors/Reproduce.cs:21-28,44-63`). Stheno uses the same child ID, density radius 2.5, cap 8, and 750 ms cooldown in both definitions (`Game/Logic/Database/SnakePit.cs:84-90`; `wServer/logic/db/BehaviorDb.SnakePit.cs:85-90`). Target swarms therefore appear stacked at Stheno's location; reference distributes them within 1.25 tiles. This is a concrete placement difference under matched arguments, with uncertain design intent.

### `Spawn` child caps persist for the behavior entry, not child lifetimes

Both `Spawn` implementations maintain a monotonic `CurrentNumber` counter and do not decrement it when a child dies (target `Game/Logic/Behaviors/Spawn.cs:25-39,50-67`; reference `wServer/logic/behaviors/Spawn.cs:26-43,46-63`). Exiting/re-entering the behavior creates fresh counter state, but existing spawned children are not removed by `Spawn.Exit` (target `:70-73`; reference state is held by the behavior instance and world insertion at `:35-43,52-59`). So `maxChildren` limits births during that behavior entry, not the number of currently alive children; spawned children have their own death/decay behavior. This mechanism aligns for the shared Snakepit Guard Spawner config (`maxChildren: 1, initialSpawn: 1`; target `Game/Logic/Database/SnakePit.cs:429-435`, reference `wServer/logic/db/BehaviorDb.SnakePit.cs:469-476`), which creates one guard and has no capacity for later births.

There is a target counter discrepancy for entries that combine a nonzero `initialSpawn` with remaining capacity: target initializes `CurrentNumber` to `InitialSpawn` and increments it again for each successful initial child (`Spawn.cs:26-39`); reference initializes to the same count but does not increment inside its initial-spawn loop (`wServer/logic/behaviors/Spawn.cs:28-43`). This can make target-side `Spawn` hit the cap earlier for such configurations. The active reference Big Creampuff initializer is a concrete example: `maxChildren: 2, initialSpawn: 0.5` computes one initial child; reference leaves the counter at one, then its 5-second cooldown can spawn a second child and reach the cap. Target Big Creampuff instead uses `SpawnOnce`, so this is a reference behavior finding rather than a like-for-like primitive comparison. See the specialized comparison for the target/reference definitions and the spawn counter validation note.

### HP threshold comparison differs at equality

Target's `HealthTransition` fires when health percentage is `<= Threshold` (`Game/Logic/Transitions/HealthTransition.cs:16-22`); reference `HpLessTransition` uses strict `<` (`wServer/logic/transitions/HpLessTransition.cs:22-27`). The shared Snakepit Guard changes phase at 60% in both DBs (`Game/Logic/Database/SnakePit.cs:380-386`; `wServer/logic/db/BehaviorDb.SnakePit.cs:408-414`). Exactly at 60%, target transitions and reference waits until health falls below 60%. This is a boundary-only timing difference, likely immaterial for many damage increments but observable with exact health values.

### Target `NoPlayerWithinTransition` includes its own host in the entity query

Target `NoPlayerWithinTransition` returns true only when both `GetNearestPlayer` and `GetNearestEntity` return null (`Game/Logic/Transitions/NoPlayerWithinTransition.cs:14-17`). The latter scans all entities in `EntityChunks` without excluding `host` (`Utils/GameUtils.cs:30-48`), and `ChunkController.HitTest` includes any entity at distance `< radius` (`Game/ChunkController.cs:98-115`). World insertion puts ordinary enemies into `EntityChunks` (`Game/World.cs:636-640`), so a live host is itself a match at distance zero for any positive radius. Consequently this target transition cannot fire while its host remains in the world. The adjacent target `NoEntityWithinTransition` explicitly excludes the host (`Game/Logic/Transitions/NoEntityWithinTransition.cs:14-19`), supporting that this is likely an omission in `NoPlayerWithinTransition`, not an intended predicate.

The shared Paper Bot places `NoPlayerWithinTransition(30, "Idle")` inside its `Attack` state (`Game/Logic/Database/Mountain.cs:272-280`); the active reference definition has the same nested transition (`wServer/logic/db/BehaviorDb.Mountain.cs:300-319`). Reference checks only for a visible player via `GetNearestEntity(dist, objType: null)` (`wServer/logic/transitions/NoPlayerWithinTransition.cs:21-24`). Whenever the target transition is evaluated, the host self-match prevents it from requesting a return to `Idle`; the logical state may therefore remain `Attack`. Whether its attack and healing behaviors continue ticking after players leave is separately gated by `Entity.TickStates`, which skips behavior ticks for entities with no active condition effects and no player nearby (`Game/Entity.cs:628-633`), so continued attacks are not implied. The same transition predicate defect applies to the nested transition in Steel Bot (`Game/Logic/Database/Mountain.cs:300-309`; reference `BehaviorDb.Mountain.cs:325-345`). This is a high-confidence target-side logic bug for active nested uses of this transition with positive distance.

## Helpers that align or need runtime-level review

- Angles in `Shoot` remain degrees at the DB call site and are converted to radians in both constructors: target `MathUtils.ToRadians` (`Game/Logic/Behaviors/Shoot.cs:45-50`) and reference `Math.PI / 180` (`wServer/logic/behaviors/Shoot.cs:35-38`). No shared-definition degree/radian conversion mismatch found.
- `TimedTransition` randomizes its initial delay over `[0, Time)` only when `randomized: true` in both implementations (target `Game/Logic/Transitions/TimedTransition.cs:20-23`; reference `wServer/logic/transitions/TimedTransition.cs:23-28`). With the flag false it starts at `Time`; after an expiry, both reload the fixed `Time` (`Game/Logic/Transitions/TimedTransition.cs:25-34`; `wServer/logic/transitions/TimedTransition.cs:29-39`). Exact perceived duration still depends on each engine runner's tick/update ordering, which this note does not infer.
- `ConditionalEffect` is structurally aligned for ordinary state-scoped invulnerability: target applies on `Enter` and removes on `Exit` unless permanent (`Game/Logic/Behaviors/ConditionalEffect.cs:12-24`); reference applies an indefinite effect on state entry and removes it on exit unless `perm` (`wServer/logic/behaviors/ConditionalEffect.cs:17-40`). Broader state lifecycle handling is covered by the engine review.
- Random sources differ globally: target `MathUtils` uses one locked `Random` (`Utils/MathUtils.cs:14-18,45-70`), while reference behavior randomness is thread-local and its accessor recreates the generator every ten accesses (`wServer/logic/Behavior.cs:14-32`). This affects random sequences and reproducibility, but does not support a deterministic direction or magnitude claim for a particular enemy.

## Review extent and limits

Reviewed the `Shoot`, `Cooldown`, `Reproduce`, `Spawn`, `TimedTransition`, `HpLessTransition`/target `HealthTransition`, `NoPlayerWithinTransition`, `ConditionalEffect`, and shared math/random helpers named above. Concrete matched usages were checked in Mountain/Beholder and nested Paper Bot/Steel Bot transitions, Spider Den/Brown Den Spider, and Snake Pit/Stheno and Snakepit Guard. State-machine execution order, other entity lookup/visibility, movement formulas, transition families beyond the named examples, and all other behavior classes were not exhaustively compared here. Database tuning differences are tracked in the separate enemy-definition reports; none of the implementation differences above establishes whether the target or 2015 reference is historically authoritative for 2014.
