# W04 — Fixed tick cadence + first frame on join

Status: done (2026-10-14). Not committed.

## What changed
- `Game/Manager.cs:1094-1118`: fixed-cadence gate. Each tick moves `TickDueAt` forward by exactly one period, never by the
  tick's start or duration. At most one tick runs per main-loop pass. A tick more than 5 periods (500 ms) late resyncs the
  schedule to now, with a warning rate-limited to 1/s. `LastTickTime` and `TotalTime` keep their meaning, and `TickDelta`
  is now diagnostic only.
- `Game/Manager.cs:75-85, 1244-1256`: test hooks. `REALM_TICK_LOAD_MS` adds a synthetic sleep per tick (off by default), and
  `REALM_TICKTRACE=1` prints one `[tick]` line per tick.
- `Game/Entities/Player.Update.cs:108` `SendJoinFrame()`: the joiner's `SendUpdate()` + `SendNewTick()`, called from Create
  (`GameServer.Handlers.cs:677`) and Load (`:734`) right after CreateSuccess is queued.
- `Networking/Client.cs:387`: `_socket.NoDelay = true`. Nagle plus Linux delayed-ACK added ~40 ms between back-to-back small writes.
- `tools/hop/tick_period.py` (new): tick-period statistics, with an optional ±tolerance gate.

## Why the extra NewTick is safe
realm-cpp increments `pending_moves_` on every NEWTICK (`src/messaging/Session.cpp:167-169`) and sends one Move per pending
tick (`:117-123`). The server credits one `AwaitingMoves` per `SendNewTick`, so the pairing holds. `ClientTimeGate` only sees
Move times (`Player.Timing.cs:27`). The client interpolates over a fixed 127 ms (`World.hpp:38`), and NewTick carries no
tickId (`Protocol.hpp:136`). No protocol or client change was needed. Because the join frame uses the normal diff state
(EntityUpdates/TileUpdates), the next tick sends nothing twice.
