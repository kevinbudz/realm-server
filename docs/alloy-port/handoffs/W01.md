# W01 — Confirm the 1 s busy-handler stall

Status: done (2026-10-14). Investigation only; no repo code changed.

## Repro
A throwaway C# console project using the same package (Microsoft.Data.Sqlite 8.0.0, SQLitePCLRaw 2.1.6) and the same
pragmas as `Database.OpenConnection`. It lived in the session scratchpad (`w01/repro`); the DB was on ext4 (`~/.cache`),
because tmpfs hides the fsync stall. The test: connection A holds `BEGIN IMMEDIATE` for about 6 ms while connection B
runs a SetKey-style open + pragmas + upsert. 50 runs per configuration, no errors unless noted.

| Config | min | median | p95 | max (ms) |
|---|---|---|---|---|
| Control, no writer | 0.05 | 0.09 | 0.42 | 3.12 |
| **Server config: busy_timeout=5000** | 1000.13 | **1000.21** | 1000.39 | 1006.24 |
| busy_timeout=100, no handler | 150.13 | 150.21 | 150.39 | 151.75 |
| busy_timeout=0 (no SQLite handler) | 150.14 | 150.18 | 150.44 | 156.59 |
| Managed callback mimicking a whole-second sleep | 1000.11 | 1000.22 | 1000.49 | 1006.15 |
| 1 ms handler installed **before** the busy pragma (overwritten) | 1000.13 | 1000.19 | 1000.36 | 1005.91 |
| **FIX: 1 ms handler after the pragmas** | 4.19 | **6.50** | 6.77 | 6.88 |
| FIX, no busy pragma, `Default Timeout=5` | 6.35 | 6.48 | 6.74 | 6.78 |
| Baseline / FIX with pooling off | 1000.37 / 6.63 (median) | | | |

## Verdict
- **The hypothesis holds.** `sqliteDefaultBusyCallback` sleeps in whole seconds on this build. The bundled `e_sqlite3`
  imports `nanosleep` but not `usleep`, so we infer it was built without `HAVE_USLEEP`.
- **Second cause, partly true:** Microsoft.Data.Sqlite 8.0.0 has its own `RetryWhileBusy` loop (read from the IL). After a
  `SQLITE_BUSY` it sleeps a fixed 150 ms and retries until `CommandTimeout`, which defaults to 30 s. That accounts for the
  150 ms rows, not the 1000 ms one.
- **Busy-snapshot path:** a stale read-then-write (`BEGIN DEFERRED`) never calls the handler, and Microsoft.Data.Sqlite then
  retries for 30 s before throwing. `SetKey` is a single autocommit statement, and the repo's only BEGIN is `BEGIN IMMEDIATE`
  (`Database.cs:354`), so neither is affected.
- **Long holds:** with the fix and a 31 s hold, the write fails at 30.75 s. `Default Timeout=5` caps that at 5.00 s.

## Decision for W03 (lead)
Install a 1 ms busy handler in `OpenConnection` **after** the PRAGMA batch, and drop `busy_timeout` from that batch. Add
`Default Timeout=5` to the connection string so a blocked command gives up after 5 s instead of 30 s.
SQLitePCLRaw 2.1.6 has **no managed** `sqlite3_busy_handler`, so call the native function directly:

```csharp
[UnmanagedFunctionPointer(CallingConvention.Cdecl)] private delegate int BusyCallback(IntPtr pArg, int count);
[DllImport("e_sqlite3", CallingConvention = CallingConvention.Cdecl)] private static extern int sqlite3_busy_handler(IntPtr db, BusyCallback cb, IntPtr pArg);
private static readonly BusyCallback BusyStepCb = BusyStep;   // must stay rooted: GC'd delegate => process abort (exit 134)
[ThreadStatic] private static long _busyStart;
private static int BusyStep(IntPtr pArg, int count) {
    if (count == 0) _busyStart = Stopwatch.GetTimestamp();
    double ms = (Stopwatch.GetTimestamp() - _busyStart) * 1000.0 / Stopwatch.Frequency;
    if (ms + 1 > 5000) return 0;
    Thread.Sleep(1); return 1;
}
// OpenConnection, after the PRAGMA batch:
int rc = sqlite3_busy_handler(conn.Handle.DangerousGetHandle(), BusyStepCb, IntPtr.Zero);
if (rc != 0) throw new InvalidOperationException("sqlite3_busy_handler rc=" + rc);
```

Gotchas:
- The delegate must be held in a static field.
- Any `busy_timeout` pragma set after the handler replaces it.
- On this build, never rely on a `busy_timeout` value below 1000 ms; it still sleeps in whole seconds.
- The `DllImport` name must match the provider's native library (`e_sqlite3`).
- The P/Invoke isn't NativeAOT-safe. The project isn't AOT, so this is fine today.
